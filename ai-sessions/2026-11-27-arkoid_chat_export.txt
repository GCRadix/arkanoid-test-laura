  the mono samples that LoadLoopSample already preloads, so the audio thread
  never locks, allocates or touches the disk. It handles gain, playback rate and
  stereo pan, smoothing each one per sample so changes don't click.

  //////////////////////////////////////////////////////////////////////////////

  // Audio thread only. No locks, no heap allocation, no file I/O: it reads the 
  preloaded mono samples.
  void CAudioManager::MixLoopVoice(float* const pOutputBuffer)
  {
          SLoopVoice& voice = m_loopVoice;

          if (!voice.isValid || (voice.pSamples == nullptr) || (voice.numFrames
  < 2) || (m_numChannels < 2))
          {
                  return;
          }

          // Read every game-thread parameter once per buffer.
          ELoopState const state = voice.state.load();
          float const targetGain = (state == ELoopState::Stopping) ? 0.0f :
  voice.targetGain.load();
          float const targetRate = voice.targetRate.load();

          // Constant-power stereo pan from the paddle-relative x (-1 = left, +1
  = right).
          float const horizontalCenter =
  (static_cast<float>(Game::g_borderRight) -
  static_cast<float>(Game::g_borderLeft)) * 0.5f;
          float const panX = std::clamp(voice.position.x.load() /
  horizontalCenter, -1.0f, 1.0f);
          float const panAngle = (panX + 1.0f) * 0.25f * 3.14159265f; // 0 .. 
  pi/2
          float const targetPanLeft = std::cos(panAngle);
          float const targetPanRight = std::sin(panAngle);

          // One-pole smoothing with a time constant of about 10 ms, so changes 
  to gain, rate and pan don't click.
          float const smoothing = 1.0f - std::exp(-1.0f / (0.01f *
  static_cast<float>(m_sampleRate)));

          // The file's sample rate can differ from the device's.
          double const sampleRateRatio = static_cast<double>(voice.sampleRate) /
  m_sampleRate;
          double const numFrames = static_cast<double>(voice.numFrames);

          float* pOut = pOutputBuffer;

          for (int i = 0; i < m_bufferLength; ++i)
          {
                  voice.gain     += (targetGain     - voice.gain)     *
  smoothing;
                  voice.rate     += (targetRate     - voice.rate)     *
  smoothing;
                  voice.panLeft  += (targetPanLeft  - voice.panLeft)  *
  smoothing;
                  voice.panRight += (targetPanRight - voice.panRight) *
  smoothing;

                  // Linear interpolation between neighbouring frames. After the
  last frame it wraps to the first.
                  auto const index0 = static_cast<sf_count_t>(voice.readPos);
                  sf_count_t const index1 = ((index0 + 1) < voice.numFrames) ?
  (index0 + 1) : 0;
                  float const fraction = static_cast<float>(voice.readPos -
  static_cast<double>(index0));
                  float const sample = voice.pSamples[index0] +
  ((voice.pSamples[index1] - voice.pSamples[index0]) * fraction);

                  float const out = sample * voice.gain;
                  pOut[0] += out * voice.panLeft;
                  pOut[1] += out * voice.panRight;
                  pOut += m_numChannels; // leave any extra channels untouched, 
  as the stereo path in CAudioMixer does

                  voice.readPos += voice.rate * sampleRateRatio;

                  while (voice.readPos >= numFrames)
                  {
                          voice.readPos -= numFrames;
                  }
          }
  }

  Design choices

  - Fractional readPos with linear interpolation: this lets
    SetLoopRate(m_timeFactor) slow the sound down smoothly in bullet time. It
    also corrects for a WAV whose sample rate differs from the device's.
  - Seamless wrap: at the last frame, interpolation continues into the first
    one, so the loop has no gap at the seam. This only sounds clean if the WAV
    itself loops cleanly.
  - One-pole smoothing instead of a fixed linear ramp: it works the same however
    often the game thread changes a target. A fade-out reaches your 0.0001
    threshold in about 90 ms, and then the voice is set back to Free.
  - Stereo only: the existing positional mixer also handles quad and 5.1
    speakers, but this example writes only channels 0 and 1. Covering surround
    would mean reusing that mixer's speaker-gain calculation. That's worth
    noting in NOTES.md.

  Things to change elsewhere for this to work

  - Remove the lastSeenState write from StartLoop. As it stands, the restart
    check above never fires, so a new ball would pick up wherever the old sound
    left off. Also move the state.store(Playing) that comes before the isValid
    check to after it.
  - Fill in SetLoopPosition: it should store x and y into m_loopVoice.position.
    Otherwise the pan only updates when StartLoop is called. In Game.cpp:481,
    also pass the paddle-relative x rather than the absolute projectile
    position.
  - Includes: std::exp and std::cos need <cmath>, and std::clamp needs
    <algorithm>. SetLoopRate already uses std::clamp, so <algorithm> is probably
    reachable already.

● I added a shared positioning helper, used it in MixFile1InNPositional, and
  implemented the loop mixer with it. The Debug|x64 build compiles and links
  without warnings. I haven't run the game, so I haven't heard the result yet.

  The build still reports a failure, from the post-build step:
  CopyRuntimeLibs.bat wasn't found when MSBuild ran from the command line. That
  step only copies the DLLs and has nothing to do with these changes.
  Arkanoid.exe itself was produced.

  The helper is in CAudioMixer (AudioMixer.h/.cpp), as two static,
  real-time-safe functions:
  - ComputeListenerDirection(relativePosition, outDirection, outDistance)
    converts a position relative to the paddle into a direction and a distance
    factor. This math was copied out of RenderAudio.
  - ComputeSpeakerGains(direction, distanceFactor, numBufferChannels) returns an
    SSpeakerGains with one gain per speaker (stereo, quad or 6-channel),
    including distance attenuation. This is the panning math moved out of
    MixFile1InNPositional, unchanged.

  Where it's used:
  - MixFile1InNPositional now gets its gains from the helper and runs one loop
    over the channels. Sound output is the same as before.
  - RenderAudio calls ComputeListenerDirection for positioned voices instead of
    doing the math inline.
  - Loop mixing: your header already declared CAudioMixer::MixLoop and an
    unimplemented ComputeStereoPan, so I implemented MixLoop rather than adding
    a separate MixLoopVoice, and removed ComputeStereoPan. MixLoop uses both
    helpers, so the ball loop now pans on quad/5.1 too, not just stereo.
    RenderAudio calls it where the placeholder comment was, and passes isRestart
    so a fresh start jumps straight to the right pan and rate.
  - Loop voice data: in SLoopVoice, panLeft/panRight became channelGains[6], so
    each speaker's gain is smoothed separately. A static_assert keeps that size
    in line with g_maxPositionalChannels.
  - Fade length: the loop's fade in/out now uses your g_loopFadeSeconds. The
    fade is linear, so a stopping loop reaches exactly 0 and is set back to
    Free.

  Three small behaviour fixes inside the helper:
  - A source sitting right on the listener used to cause a divide by zero. It
    now counts as straight ahead with no attenuation. For the loop this matters:
    a NaN would get stuck in the smoothed gains and silence it for the rest of
    the session.
  - The cosine is clamped before acosf, so rounding can't produce a NaN on
    surround setups.
  - The surround default: case no longer zeroes six variables that were already
    zero.

  Still open:
  - StartLoop still writes lastSeenState, which only the audio thread should
    touch. Because of that, isRestart never becomes true, so a new ball won't
    rewind the loop to the start.
  - SetLoopPosition is still empty, and Game.cpp:481 passes it the absolute x
    rather than the x relative to the paddle. Panning works anyway, because
    StartLoop is called every frame with the paddle-relative position.
  - g_baseTimeFactor isn't used yet: SetLoopRate stores m_timeFactor directly
    (clamped), so the loop plays at 1.3× at the start of a game.

  Nothing is committed yet. Say if you want me to fix any of the open items.

❯ why are the playingVoices being erased after reading them in renderaudio?     

  Read 1 file (ctrl+o to expand)

● Erasing a voice is how a one-shot sound ends. SPlayingVoice has no loop flag,
  no stop call and no "finished" state, so the voice list is the only record of
  what is playing. When a sound has finished, removing it from m_pPlayingVoices
  is the only way to stop mixing it.

  How a voice ends

  At AudioManager.cpp:227–261, RenderAudio loops over m_pPlayingVoices. For each
  voice:

  1. MixFile1InNPositional or MixFileNInN reads up to one buffer of frames
     (m_bufferLength, 2048) from the voice's open SNDFILE* with sf_readf_float,
     mixes them in, and returns how many frames it read.
  2. If it read fewer than 2048 frames, the file has reached its end. This was
     the last partial buffer, which has already been mixed, so the voice is
     erased.
  3. Invalid or null voices (the else branch around line 258) are also erased.

  The loop runs from the back of the vector to the front (for (int i = size - 1;
  i >= 0; --i)). Erasing element i shifts only the elements after it, which
  have already been processed, so no voice is skipped.

  Erasing does more than remove an entry. Each shared_ptr<SPlayingVoice> there
  is the last owner of its voice, so erasing destroys the voice, and
  ~SPlayingVoice calls sf_close(pFile) (PlayingVoice.h:30). Erasing is therefore
  also what closes the file handle.

  Why this design is a problem

  It works, but it breaks all three real-time rules in the brief, and CLAUDE.md
  marks it as a pattern not to copy:

  - Unsynchronized shared vector. Play on the game thread calls push_back on the
    same vector while the audio thread erases from it, with no lock. A
    push_back that reallocates during the audio thread's loop invalidates the
    element it is reading. That is undefined behaviour and a possible crash.
  - Freeing memory on the audio thread. The erase releases the last shared_ptr,
    so the audio thread frees the SPlayingVoice and the shared_ptr's bookkeeping
    memory.
  - File I/O on the audio thread. sf_close runs inside the callback, on top of
    the sf_readf_float reads that already happen there every buffer.
  - Mono outputs. If the output device has only one channel,
    MixFile1InNPositional returns 0, so a positioned voice is erased on its
    first buffer without ever being heard.
  - The pointer returned by Play. Play returns a raw SPlayingVoice* that
    UpdatePosition later compares against the list. After an erase, that pointer
    refers to freed memory. UpdatePosition only compares addresses, so it
    doesn't crash. But a new voice allocated at the same address would make it
    update the wrong voice.

  How the loop voice avoids this

  The ball loop doesn't follow this pattern. SLoopVoice is a member of
  CAudioManager, so it is never allocated or freed during play, and its samples
  are loaded into memory at startup. It doesn't end by being erased: the game
  thread sets the Stopping state, and the audio thread fades it out and sets it
  back to Free. The usual fix for one-shot voices works the same way: a fixed
  pool of voice slots with a state field, and a lock-free queue that hands
  finished voices back to the game thread to close and free.

❯ In MixFileNInN how is the loop realized?                                      

● The loop is the if (loop) block at AudioMixer.cpp:28–35. It repeats a file by
  seeking back to the start whenever a read runs out. Only the music uses it:
  all three MixFileNInN calls in RenderAudio pass loop = true. The ball loop has
  its own code in MixLoop and doesn't go through this.

  numFramesRead = sf_readf_float(pFile, pMixBuffer, requestedSamples);

  if (loop)
  {
          while (numFramesRead != requestedSamples)
          {
                  sf_seek(pFile, 0, SF_SEEK_SET);
                  numFramesRead += sf_readf_float(pFile, (pMixBuffer +
  numFramesRead), (requestedSamples - numFramesRead));
          }
  }

  Step by step

  1. Normal read: it reads up to one buffer (2048 frames) into the scratch
     buffer m_pMixBuffer.
  2. End of file: if the file ends partway through, sf_readf_float returns fewer
     frames than requested.
  3. Wrap: it seeks back to frame 0 and reads the missing frames into the rest
     of the scratch buffer, after the frames it already has.
  4. Repeat: the while keeps doing this until the buffer is full, so a file
     shorter than one buffer would loop several times within a single buffer.
  5. Mixing: the mixing loops below always receive a full buffer. So the
     function returns 2048, and RenderAudio never sees the music end.

  There's no state for the loop. The file's own read position, held inside the
  open SNDFILE*, is the playback position, and seeking is the only way to wrap.
  That means the loop involves file I/O inside the audio callback every time it
  wraps.

  Bug: the second read lands in the wrong place

  pMixBuffer + numFramesRead offsets the pointer by frames, but the buffer holds
  interleaved samples, one float per channel per frame. The music files are
  stereo, so the offset should be numFramesRead * numFileChannels.

  Example: 500 frames remain before the end of the file.

  - The first read fills floats 0–999.
  - The wrap read starts at float 500, which is only frame 250. It overwrites
    the last 250 frames of the file's ending with the file's beginning.
  - It writes 1548 frames, which ends at frame 1798. The last 250 frames of the
    buffer keep the zeros from the std::fill at the top of the function.

  So at every music loop point the end of the track is cut short, and about 250
  frames (around 5 ms at 48 kHz) of silence follow. You may hear that as a click
  or a short dropout at the seam.

  The fix is one line:

  numFramesRead += sf_readf_float(pFile, pMixBuffer + (numFramesRead *
  numFileChannels), requestedSamples - numFramesRead);

  Smaller issues in the same function

  - Possible hang: if a read returns 0 (empty or unreadable file), the while
    loop never ends and the audio callback hangs. A framesRead == 0 guard would
    break out of it.
  - Wrong stride: the mixing loops index the scratch buffer with channelsToWrite
    instead of numFileChannels. When the output has fewer channels than the
    file, they read the interleaved data with the wrong step.
  - Buffer overrun on a mono device: the scratch buffer is sized for the
    output's channel count (bufferLength * numChannels), but sf_readf_float
    writes frames * numFileChannels floats. A stereo file on a mono device
    therefore writes past the end of the buffer on every read, loop or not.

  I haven't changed anything. Do you want me to apply the offset fix, and the
  framesRead == 0 guard with it?

❯ why is it problematic to read from the disk in the audiothread                

● The audio thread has a hard deadline, and a disk read can take an
  unpredictable amount of time. Nothing guarantees how long a read will take, so
  even an occasional slow one costs you audio.

  The deadline

  PortAudio calls StreamCallback once per buffer and expects it to return before
  the sound card runs out of samples. This project uses 2048-frame buffers, so
  at 48 kHz the callback has about 42.7 ms (2048 / 48 000). In practice it has
  less, because the driver and the OS need part of that time too. If the
  callback is late, the device has no data. That's a buffer underrun, which you
  hear as a click, a stutter or a gap. Every sound drops out together, music
  included, not just the voice that was slow.

  What matters is the worst case, not the average. A callback that takes 1 ms a
  thousand times and 60 ms once still glitches once.

  Why disk reads have no upper bound

  sf_readf_float ends up as ReadFile on Windows. Usually the data is already in
  the OS file cache and the read is fast, but a single read can also hit any of
  these:

  - Cache misses: the data has to come from the drive. On a hard disk that's a
    seek, about 5–15 ms each, and one read can need several. SSDs are faster,
    but they still have occasional slow spikes.
  - A drive that has to wake up: power saving can spin a disk down or put an SSD
    into a low-power state. Waking it can take hundreds of milliseconds or even
    seconds.
  - Other software: antivirus scanners intercept file access, indexers and
    backup tools compete for the disk, and assets on a network drive add network
    delays.
  - Locks you don't control: the file system and the C runtime take internal
    locks. If a lower-priority thread holds one of them, the high-priority audio
    thread waits until that thread gets scheduled again. This is called
    priority inversion.
  - Being descheduled: a system call that blocks gives up the CPU. When the
    thread runs again is up to the scheduler.

  None of these show up in a profiler on your machine. They show up as
  occasional glitches on someone else's.

  Where this code does it

  - Every voice reads every buffer: MixFileNInN and MixFile1InNPositional call
    sf_readf_float for the music and for each playing voice in every callback.
  - Music loop: when the music loops, sf_seek runs in the callback.
  - Closing files: erasing a finished voice runs ~SPlayingVoice → sf_close in
    the callback, which is a file system call plus freeing memory.

  It sounds fine in practice because the files are small, the OS keeps them
  cached after the first play, and 43 ms is a generous buffer. That's luck, not
  a guarantee. If you shrank the buffer to a usual game size (256–512 frames,
  about 5–10 ms), the margin would mostly be gone.

  What to do instead

  - Preload short sounds: decode them into memory at startup, and the audio
    thread only copies floats. The ball loop works this way (LoadLoopSample,
    then MixLoop reads pSamples).
  - Stream long sounds from a worker thread: a background thread reads the file
    ahead into a lock-free ring buffer, and the audio thread only reads from
    that buffer. Disk delays then hit the worker, and the buffered audio covers
    them. This is the usual fix for the music.
  - Clean up off the audio thread: opening, closing and freeing happen on the
    game thread or a worker. The audio thread hands finished voices back through
    a lock-free queue.

  The same reasoning is behind the brief's other two rules. Locks and heap
  allocation also have no upper bound on how long they can take (waiting on
  another thread, or on the allocator's internal lock), so they don't belong in
  the audio thread either.
